# Система заявок

## О проекте

«Система заявок» — небольшое веб-приложение для приёма и обработки заявок. Пользователь сможет создавать заявку, а сотрудник — просматривать список, открывать карточку заявки и менять её статус.

На текущем этапе подготовлены архитектура, базовый Express backend, PostgreSQL и Prisma-модель заявки. Прикладная логика заявок, API заявок и пользовательский интерфейс ещё не реализованы.

## Цель проекта

Создать понятный и расширяемый проект для тестового задания, который легко развивать по этапам и объяснять на собеседовании. Архитектура разделяет интерфейс, HTTP-слой, бизнес-правила и доступ к данным, не усложняя небольшой проект.

## Функциональные требования

- Создание заявки пользователем.
- Просмотр сотрудником списка заявок.
- Просмотр подробной информации по заявке.
- Изменение статуса заявки.
- Хранение заявок в реляционной базе данных.
- Предоставление REST API для frontend.
- Серверная валидация входящих данных.

Требования будут реализовываться последовательно в следующих этапах; в этом этапе они определяют границы архитектуры.

## Архитектура

Поток обработки запроса:

```text
Frontend
   ↓
REST API
   ↓
Routes
   ↓
Controllers
   ↓
Services
   ↓
Repositories
   ↓
Prisma
   ↓
PostgreSQL
```

- **Frontend** отображает страницы, получает пользовательский ввод и вызывает REST API через сервисы.
- **REST API** является контрактом взаимодействия между frontend и backend.
- **Routes** сопоставляют HTTP-метод и URL с нужным контроллером.
- **Controllers** принимают HTTP-запрос, передают данные в сервис и формируют HTTP-ответ.
- **Services** содержат бизнес-логику: правила создания заявки и смены её статуса.
- **Repositories** изолируют операции чтения и записи данных.
- **Prisma** будет связывать репозитории с PostgreSQL.
- **Schemas** содержат Zod-схемы для серверной валидации входящих данных до выполнения бизнес-логики.
- **Middleware** будет обрабатывать общие задачи HTTP-уровня, например ошибки и валидацию.
- **Config** будет централизованно получать и проверять переменные окружения.

Такое разделение оставляет контроллеры тонкими, а бизнес-логику и доступ к данным — независимыми от Express.

## Модель данных

### Database

Данные хранятся в PostgreSQL. Prisma описывает структуру базы, создаёт миграции и генерирует типизированный клиент для будущего backend-кода.

### Request model

В базе создана сущность `Request`.

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | integer | Уникальный идентификатор с автоматическим увеличением |
| `applicantName` | string | ФИО заявителя |
| `email` | string | Email заявителя |
| `phone` | string | Телефон заявителя |
| `subject` | string | Тема заявки |
| `description` | string | Описание заявки |
| `createdAt` | datetime | Дата и время создания, задаётся автоматически |
| `status` | enum | Текущий статус; по умолчанию — `NEW` |

Все поля заявки, кроме автоматически формируемых `id`, `createdAt` и `status`, обязательны.

### Status

| Техническое значение | Отображаемое значение |
| --- | --- |
| `NEW` | Новая |
| `IN_PROGRESS` | В работе |
| `COMPLETED` | Выполнена |
| `REJECTED` | Отклонена |

Статус хранится в PostgreSQL как enum, поэтому база принимает только перечисленные значения.

### Migration

Для создания и применения новой миграции в локальной разработке используйте из папки `backend`:

```bash
pnpm exec prisma migrate dev --name create_request
```

## API

Базовый путь API: `/api`.

### Реализовано

#### POST /api/requests

Создаёт новую заявку. Поля `createdAt` и `status` клиент не задаёт: время создаётся автоматически, а статус всегда начинается со значения `NEW`.

Предполагаемое тело запроса:

```json
{
  "applicantName": "Иван Иванов",
  "email": "ivan@example.com",
  "phone": "+7 700 000 00 00",
  "subject": "Вопрос по заказу",
  "description": "Нужна помощь с заказом."
}
```

Успешный ответ (`201 Created`):

```json
{
  "success": true,
  "data": {
    "id": 1,
    "applicantName": "Иван Иванов",
    "email": "ivan@example.com",
    "phone": "+7 700 000 00 00",
    "subject": "Вопрос по заказу",
    "description": "Нужна помощь с заказом.",
    "createdAt": "2026-08-18T00:00:00.000Z",
    "status": "NEW"
  }
}
```

При ошибке валидации сервер отвечает `400 Bad Request`:

```json
{
  "success": false,
  "message": "Ошибка валидации",
  "errors": {
    "email": ["Укажите корректный email"]
  }
}
```

Также возможен `500 Internal Server Error` при непредвиденной ошибке сервера.

### Запланировано

#### GET /api/requests

| Метод | URL | Назначение |
| --- | --- | --- |
| `GET` | `/api/requests` | Получить список заявок |

Основные ответы: `200 OK` — список получен; `500 Internal Server Error` — внутренняя ошибка.

#### GET /api/requests/:id

| Метод | URL | Назначение |
| --- | --- | --- |
| `GET` | `/api/requests/:id` | Получить одну заявку по идентификатору |

`id` передаётся в параметре URL. Endpoint вернёт полную карточку заявки со всеми полями модели, включая дату создания и текущий статус. Тело запроса не требуется.

Основные ответы:

- `200 OK` — заявка найдена и возвращена.
- `400 Bad Request` — `id` имеет неверный формат.
- `404 Not Found` — заявки с таким `id` нет.
- `500 Internal Server Error` — внутренняя ошибка сервера.

#### PATCH /api/requests/:id/status

| Метод | URL | Назначение |
| --- | --- | --- |
| `PATCH` | `/api/requests/:id/status` | Изменить статус заявки |

Предполагаемое тело запроса:

```json
{
  "status": "IN_PROGRESS"
}
```

Основные ответы: `200 OK` — статус изменён; `400 Bad Request` — неверный `id` или статус; `404 Not Found` — заявка не найдена; `500 Internal Server Error` — внутренняя ошибка.

## Запуск проекта

Для локальной работы скопируйте `.env.example` в `.env`, а `backend/.env.example` — в `backend/.env`. Первый файл используется Docker Compose, второй — backend и Prisma. Затем запустите PostgreSQL командой `docker compose up -d`, перейдите в `backend`, выполните `pnpm install` и `pnpm dev`. Проверить backend можно запросом `GET /health`. Полные инструкции для frontend появятся вместе с интерфейсом.

## Git workflow

- Для каждого этапа создаётся отдельная тематическая ветка.
- Изменения проверяются перед коммитом, в репозиторий не попадают секреты, зависимости и локальные файлы окружения.
- Коммиты формулируются кратко в стиле Conventional Commits.
